# 02: 一条启动配置能一键启停，日志实时滚出来

**What to build:** 在面板里点「启动」，命令真的在项目目录下跑起来，输出实时出现在面板里并自动跟随；点「停止」，进程连同它 fork 出的子进程一起消失，端口释放。这一票让插件从"能存配置"变成"能干活的工具"。

**Blocked by:** 01 (面板装得上，一条启动配置能存住)

**Status:** ready-for-agent

- [ ] 点启动，命令在项目目录下执行，该启动配置的环境变量已注入
- [ ] 输出实时出现在面板里（无需刷新页面），默认跟随到底；用户向上滚动后停止跟随，滚回底部恢复跟随
- [ ] 点停止后项目里不残留 java 进程、端口被释放（用 `ps aux | grep java` 与端口探测验证）
- [ ] 重启 = 停止 + 启动，新进程不混入上一次的输出
- [ ] 插件停用 / DSH 退出时，仍在跑的进程被回收
- [ ] 环境变量里密钥类值（`*_KEY`/`*_SECRET`/`*_TOKEN`/`*PASSWORD`）在界面与日志中均被掩码
- [ ] 输出按行切分：跨 chunk 的半行拼接、`\r` 进度行只保留最后一次覆写、ANSI 转义剥离（单元测试覆盖三种情况）
- [ ] 启动失败（命令不存在、目录不存在）时面板显示可读原因，不抛栈

## Comments

**实现记录（2026-09-12）**

- Host 新增运行注册表（`src/runtime.ts`）：一条启动配置 = 一个受管进程，走 DSH `shell` 服务的公开契约（`resolve` / `start` / `ShellProcess.readOutput` / `kill`）；输出按 250ms 定时泵入内存环形缓冲（5000 行，超限从头部丢弃并标 `dropped`）。为什么由宿主采集而不是客户端拉取时顺带采集：客户端轮询慢一点就会丢输出。
- 日志接缝（`src/lines.ts`）三个纯函数：跨 chunk 半行拼接、`\r` 覆写只留最后一次、ANSI 剥离、密钥值掩码。
- 新增 4 个 RPC：`start` / `stop` / `read` / `runs`；客户端 800ms 轮询 `runs`（所有配置的状态点）+ `read`（当前配置的增量日志）。切换启动配置时清空本地缓冲，避免串台。
- 自动跟随：只有滚动位置贴底时才跟随，用户上滚看历史不会被拽回去。
- 密钥掩码两处：日志里替换为 `****`；界面里密钥类变量的输入框用 `password` 类型。
- 插件停用 / DSH 退出时回收：`ctx.effect` 的清理函数里 `clearInterval` + `registry.dispose()`（只杀仍在跑的，已自然退出的不碰——这条是测试先发现实现有 bug 才补上的）。
- **验证证据**：本包 28 项测试全绿。新增 9 项运行注册表契约测试（假 shell 驱动：启动参数透传、增量读取、半行拼接、自然退出 0/非 0、停止调 kill、dispose 回收、密钥掩码、环形丢弃、三类可读错误）+ 5 项日志行测试。
- **真机实测（2026-09-12，用户在界面上跑）**：`mvn -o -pl kun-ai-web -am spring-boot:run` 在 AI-SPACE 工作区下首先因工作目录不对而失败（`Could not find the selected project in the reactor`）；改到 kun-ai 工作区后又因 `-am` 让 run 目标施加到父工程而失败（`Unable to find a suitable main class`）。两次都是**命令/工作目录配置问题，不是插件问题**——日志面板把完整 Maven 输出实时流了出来，状态行正确显示 `已退出（码 1） · 已缓存 40 行`。结论已回写进 spec 与票 05：导入器生成的 run 命令**不能带 `-am`**。
- **仍未验证**：一条**能跑起来**的命令（Spring Boot 真正启动）的实时滚动效果，以及停止后的 `ps`/端口检查。

**Spec 轴评审处理（2026-09-12）**

| 评审发现 | 处理 |
| --- | --- |
| 自动跟随在突发输出时自断：追加后才量高度，一次涌入 >80px 就被误判成"用户上滚" | 改为 scroll 事件维护 `pinnedRef`，追加前就已确定是否贴底 |
| 启动失败原因基本不可达：shell 契约里 spawn 失败也以 `killed` 收场，而代码把 `killed` 一律记"已停止" | 区分"我们主动停的"（`stopRequested`）与"没起来就死的"：后者记 `failed` + 可读原因 |
| 退出码映射混淆：自然非 0 退出被算作"启动失败" | 自然退出一律 `exited` 并如实带出退出码；`failed` 只留给进程没起来；界面把 127 直接显示为「命令不存在（码 127）」 |
| 重启竞态：上一代在飞的读取会把旧偏移写回，导致新进程前 N 行不显示 | 客户端加代次校验（`genRef`）丢弃过期结果；宿主对 `from > next` 整份重发并标 `dropped` |
| 裸 `\r` 进度刷新（curl/mvn 进度条）不产行，全堆在 `pending` 里无界增长且面板一行不显示 | 每轮泵把含 `\r` 的 pending 收成一行（只保留最后一次覆写）；pending 超过 64KB 截断成行 |
| `cleanLine` 对行尾 CR（CRLF 输出）返回空串 | 行尾 `\r` 视为行尾而非覆写，取它前面的内容；补 CRLF 测试 |
| 截断静默：`read` 的 `dropped` 与本地 `slice(-4000)` 丢行无提示 | 两处都置 `truncated`，在日志说明行显示"早期日志已被丢弃" |
| `stop()` 在 SIGTERM 宽限期内抢报"已停止" | 改为等下一次泵看到进程真的退出再翻转；`start` 允许重启一个"已请求停止但还在宽限期"的进程 |
| 运行态缺「启动中」 | **未实现**：需要就绪判据（端口或日志模式），不在本票范围，留待后续票 |
| `const cfg = config ?? defaultState()` 被判为死代码 | **不改**：它喂给 hooks（runKey 等），hooks 必须无条件执行，`null` 分支的值只是不渲染 |
